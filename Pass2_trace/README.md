# Задание 2: инструментирующий Pass — трасса (User <- Operand) и частые паттерны

Собирается **динамическая** трасса использования IR-инструкций
`(User <- Operand)` приложения (только логический модуль `app.c`),
скомпилированного с `-O2` и `-Os`, и проводится частотный анализ
повторяющихся паттернов длины окна 1–5 инструкций.

## Состав

| Файл              | Назначение                                                        |
|-------------------|-------------------------------------------------------------------|
| `TracePass.cpp`   | LLVM Pass (плагин для clang, new PM): статический id каждому      |
|                   | экземпляру инструкции + вставка `traceLogger(user_id, operand_id)`|
| `trace.c`         | рантайм-логгер: буферизованная запись бинарной трассы в `TRACE_FILE` |
| `run_trace.sh`    | запуск приложения на N секунд и аккуратное завершение (SIGTERM)   |
| `analyze.py`      | анализ частых паттернов (окна 1–5) по статической карте и трассе  |
| `maps/`           | статическая карта `id -> инструкция` (генерируется Pass'ом)       |
| `traces/`         | бинарные трассы (gitignored, ~6 ГБ каждая)                        |
| `reports/`        | итоговые отчёты анализа (`report_opt.txt`, `report_os.txt`)       |

## Как собрать и запустить

```sh
make trace-pass-lib             # собрать Pass2_trace/libTracePass.so
make app-trace-opt app-trace-os # инструментированные приложения (-O2 и -Os)
make trace-ir                   # инструментированный IR для просмотра (IR/app-*-tr.ll)

make trace-run TRACE_SECONDS=6  # запустить на 6 с, собрать обе трассы
make trace-report TRACE_LIMIT=20000000   # анализ первых 20M событий

# вручную (окно откроется, если есть дисплей):
TRACE_FILE=Pass2_trace/traces/trace_opt.bin ./build/app-trace-opt
# завершить: Ctrl+C (SIGINT) или kill -TERM — буфер будет сброшен
```

## Как устроен Pass (`TracePass.cpp`)

1. Pass регистрируется через `registerOptimizerLastEPCallback` — он
   срабатывает **в конце** пайплайна оптимизации, поэтому трасса
   соответствует реально исполняемому IR `-O2`/`-Os`, а не исходному.
2. Проверяется модуль: `M.getSourceFileName()` заканчивается на `app.c` —
   инструментируются только функции логического модуля (sim.c/start.c/
   trace.c пропускаются).
3. Каждой инструкции в `app()` присваивается стабильный числовой id
   (порядок: функция -> блок -> инструкция), карта `id -> (opcode,
   функция, печать инструкции)` пишется в файл `TRACE_MAP`.
4. Для каждой пары `User`/`Operand`, где `User` — **не** phi-инструкция
   (phi* пропускаются по условию задания), а `Operand` — инструкция
   (константы, аргументы и basic block'и не учитываются), перед `User`
   вставляется `call void @traceLogger(i64 user_id, i64 operand_id)`.
   Phi-инструкции при этом остаются видимы как операнды.

## Формат трассы

```
[8]  magic "LLVMTR01"
[8]  размер события = 16
[16] событие: uint64 user_id, uint64 operand_id   (little-endian)
```

Запись буферизованная (2 МБ), сброс каждые 1e6 событий и по SIGTERM/
SIGINT — потеря данных при завершении минимальна. Скорость записи
~70 Mev/с, файл ~16 МБ/с.

## Анализ паттернов (`analyze.py`)

Каждое событие превращается в символ `<user_opcode><-<operand_opcode>`
(режим `--user-only` — только user opcode). По потоку символов
подсчитываются все **пересекающиеся** n-граммы для n = 1..5; для каждого
n выдаётся топ паттернов с количеством, долей от всех окон и покрытием
топ-10. Данные первого фрагмента трассы (20M событий, ~0.3 с работы)
устойчивы: доли паттернов совпадают уже при 200K событий, так как
доминирует циклическое ядро счёта диффузии.

## Результаты (-O2)

За 6 с собрано **422M событий** (71 Mev/s), 138 инструкций в `app()`.
Анализ: 20M событий, 0 неизвестных id.

Топ user-инструкций (доля от всех событий):

| opcode | доля |
|--------|------|
| getelementptr | 30.70% |
| fadd | 15.32% |
| load | 12.76% |
| call (т.ч. llvm.fmuladd) | 10.23% |
| add | 7.74% |
| icmp / br / store / and | по ~5.2% |
| trunc | 2.59% |

Топ паттернов окна 1 (User <- Operand):

| паттерн | доля окон | смысл |
|---------|-----------|-------|
| `getelementptr<-phi` | 20.47% | вычисление адреса строки `u[y][x]` от индуктивной phi |
| `load<-getelementptr` | 12.76% | чтение элемента сетки |
| `getelementptr<-add` | 10.21% | адресация по инкременту индекса |
| `fadd<-load` | 10.21% | сложение загруженных соседей |
| `fadd<-fadd` | 5.10% | цепочка сложений пятиточечного лапласиана |
| `call<-load` | 5.10% | `llvm.fmuladd(u, -4.0, sum)` |
| `call<-call` | 5.10% | вторая `llvm.fmuladd` с коэффициентом alpha |
| `store<-getelementptr` | 2.58% | запись результата в `next_u` |

Все четыре инструкции `llvm.fmuladd`/`fadd`/`store` из тела диффузионного
цикла попадают в топ; получается скланный паттерн вычисления ядра:

```
load u[y+1][x], load u[y-1][x], load u[y][x+1], load u[y][x-1],
fadd, fadd, fadd, fmuladd(u, -4.0, sum), fmuladd(*, alpha, u),
store -> next_u[y][x]
```

Паттерны длины 2–5: топ-1 длиной 5
`getelementptr<-phi → load<-getelementptr → getelementptr<-add →
getelementptr<-phi → load<-getelementptr` (5.11% всех окон; то же ядро,
сдвинутое по фазам развёрнутого цикла). Топ-10 окна 2 покрывает 53.7%
всех окон, окна 5 — 35.9%. Группы паттернов с долей ~2.55–2.6% — это
управление циклами (`icmp<-add`, `br<-icmp`, `add<-phi`, `trunc<-phi`) и
граничные диапазоны.

## Результаты (-Os)

Почти идентичны `-O2`: 391M событий за 6 с (66 Mev/s), 119 инструкций;
те же топ-паттерны с теми же долями (максимальное отличие — сотые доли
процента, погрешность выборки). Это ожидаемо: и `-O2`, и `-Os` векторизуют
внутренний цикл и выдают одинаковый порядок инструкций горячего ядра;
отличия IR касаются лишь холодного кода инициализации/вывода.

## Выводы

1. Доминирует одно ядро: цикл пятиточечного лапласиана (~20 событий на
   итерацию, ~95% всей динамики). Всё остальное (инициализация, копирование,
   цветовой вывод) — десятые доли процента.
2. Самый частый одиночный паттерн — `getelementptr<-phi` (20.5%): адресная
   арифметика от индуктивной переменной — типичная "горячая" зависимость
   для скалярных циклов.
3. Паттерны длины 5 выводятся из паттернов длины 1–2: длинные частые
   цепочки — это просто несколько коротких, склеенных развёрнутым
   векторным циклом.
4. -O2 и -Os дают практически одинаковую трассу горячего цикла.

## Замечания

- Трассы занимают ~6 ГБ каждая (gitignored); отчёты и карты в репозитории
  воспроизводимы командами выше.
- Сигнал SIGTERM/SIGINT корректно сбрасывает буфер и закрывает файл;
  `kill -9` теряет не более 2 МБ хвоста.
